## Diagnosis
1. The controller's local axes (from the quaternion) showed its pointing axis toward robot −y (right).
2. Upstream check (CLAUDE.md OSS rule): `XR-Robotics/XRoboToolkit-Teleop-Sample-Python`
   `common/base_teleop_controller.py::_process_xr_pose` uses the same `R_HEADSET_TO_WORLD`
   ([[0,0,−1],[−1,0,0],[0,1,0]]), the same conjugation R·q·R⁻¹ and the same world-frame delta
   q2·q1⁻¹ (`utils/geometry.py::quat_diff_as_angle_axis`) → our math matches the reference.
3. **Headset facing** (headset −z in the robot frame) in the recordings: runs 1-2 **−100° / −103°**;
   the earlier position axis checks **+4° / −1°**. The operator had turned ~100° to the right (toward
   the PC/arm) without recentering. Then "twist about my forward" = robot −y and "tip down about my
   left" = robot +x: exactly the data, signs included. **No code bug.**
4. A wrong recentre/facing also breaks POSITION control (hand forward → arm right): a safety gap.

## Change: facing guard (sender)

  the headset"), FAULT if engaged. Status line shows `facing ±N deg`.
- Tests: `test_facing_away_refuses_engage_and_faults`, `test_headset_facing_from_live_recordings`
