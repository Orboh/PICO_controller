# Log 032 — Why PICO episodes are jerkier than leader episodes, and two fixes tested offline (2026-11-01)

## Question (Suraj): is the jerk due to the speed restriction?
Mostly no. Measured on the pilot datasets (leader `…_20261031_153158` ep 0/2/3/4, PICO `…_20261101_170706` ep 0/1):
| | leader | PICO |
|---|---|---|
| jerk of the recorded joints (moving frames) | 27-39 k | 45 k |
| frames where the commanded step doubles or halves | 16-17 % | 61-63 % |
| share of step-size energy at 8-12 Hz | 10-12 % | 25-27 % |
| command at the speed cap | — | 3-5 % (but 71-94 % of the top-5 % jerk spikes sit at a cap change) |
| command stands still one frame, then jumps | 0-1 | 20-28 per episode |
Causes: (1) **rate mismatch**: sender 50 Hz, lerobot-record takes the newest command at 30 fps → 1 or 2 sender
steps per frame → small/big/small steps, a ~10 Hz wobble; real on the arm while recording (it is driven at 30 fps).
(2) hard cut at the speed limits (no ease in/out). (3) PICO input gaps (headset side; target waits, then jumps).

## Fixes (both opt-in, defaults unchanged)
- Rate: `--hz 60` (2 steps per recorded frame). `scripts/gate4_sender.sh` reads `HZ` (default 50).
- Ease in/out: `TeleopConfig.max_joint_acc_dps2` / `--max-joint-acc-dps2` (`ACC` in gate4_sender.sh): trapezoidal
  joint tracking in `ArmTeleop.step()` (speed ≤ 45°/s, change of speed ≤ acc·dt, brakes in time; can end ≤ 0.5° inside the 3° guard because the guard is
  checked on the IK answer, not on the eased joints: test keeps ≥ 2.5°, log-035).
  Only while ENGAGED; release / FAULT / HOLD still stop at once (`qd` reset). Test
  `test_acceleration_limit_eases_in_without_overshoot_and_stops_on_release`. Suite **116 passed**.

## Offline test bench (scratchpad `jerkbench.py`)
Real PICO input of the pilot run (`runs/pilot-pico-3`), controller at the chosen rate, sampled like the recorder
(newest command every 1/30 s). Validated: 50 Hz gives jerk 40 k / 65 % doubling (recorded: 45 k / 61-63 %).
| setting | ep 0 window (95-210 s): jerk / doubling / change vs today (median, 95 %) | ep 1 window: jerk / doubling |
|---|---|---|
| 50 Hz, no acc (today) | 40.3 k / 65 % / 0, 0 | 66.0 k / 67 % |
| 50 Hz, acc 300°/s² | 34.5 k / 64 % / 0.09°, 0.96° | 50.6 k / 65 % |
| **60 Hz, acc 300°/s²** | **22.5 k / 36 % / 0.11°, 1.10°** | **22.3 k / 19 %** |
| 60 Hz, acc 200°/s² | 16.6 k / 25 % / 0.73°, 2.27° | 15.7 k / 13 % |
| 100 Hz, acc 300°/s² | 23.8 k / 36 % / 0.34°, 1.18° | 27.9 k / 26 % |
- Rate matching is what matters (50 Hz + acc alone barely helps; 100 Hz is not better than 60).
- **Recommended to try on the arm: 60 Hz + 300°/s²**: jerk −44 % / −66 %, below the leader range, path within
  ~1° of today's (95 %). 200°/s² is smoother but trails by 2°+.
- Limits: the replay input is the 50 Hz sender log (real PICO ~60-80 Hz); the ep 1 window's "change vs today"
  is not comparable (walls/history differ without the recorder's resets).
- Not yet on the arm. Use: `HZ=60 ACC=300 bash scripts/gate4_sender.sh <tag>`.
